# Frontend work for Phases 02 to 06

The backend for these phases is exposed through the admin app's `/rpc` oRPC route, except image upload signing at `POST /api/upload` and Better Auth's `/api/auth/*`. Build the screens below against the listed procedures. Use the existing `apps/admin/src/orpc/query.ts` client, TanStack Query for server state, and React Hook Form with Zod for forms. Keep list filters, sort, and cursors in the URL. Invalidate affected list and detail queries after mutations.

## Phase 02: admin shell

- Create the protected `(admin)` route group and shared visual shell: desktop sidebar, mobile sheet navigation, top bar, breadcrumbs, user menu, theme switch, and sign out. Call `admin.me` for name, email, image, role, and permissions. Filter navigation entries using returned permissions; server authorization remains authoritative.
- Guard each protected `page.tsx` with `requireAdmin()`. For pages needing a specific permission, check it in the page and show a permission screen. Put `loading.tsx`, `error.tsx`, and `not-found.tsx` in the route group. Redirect `UNAUTHORIZED` RPC errors to `/sign-in?next=...`; render `FORBIDDEN` as a permission message.
- Replace the status home page with a simple welcome for now. Use `/` for Overview; reserve dashboard charts for Phase 16. Verify the shell at 360, 768, and 1280 px in both themes.

## Phase 03: team and invitations

- Build `/team` with members table: name, email, role, status, date, cursor pagination, and actions to change role, suspend, or restore. Consume `team.members.list` and `team.members.update`. Only owners see these pages/actions. Confirm suspension or owner demotion; show the last-owner conflict message.
- Build `/team/invitations` with pending, expired, accepted, and revoked invitation states; create form with email and role; revoke and resend actions; copyable invite link shown once after create/resend. Consume `team.invitations.list`, `.create`, `.revoke`, and `.resend`. Treat the raw link as sensitive and clear it on navigation.
- Build public `/invite/[token]`: inspect invitation via `team.invitations.inspect`; show email, role, expiry, and invalid/expired/revoked/used messages. A signed-in user with the invited email calls `team.invitations.accept({ token })`; a new user submits name and a password of at least 12 characters to `team.invitations.accept({ token, name, password })`. Route new invitees to sign in after acceptance (`signInRequired: true`), and existing signed-in invitees to the admin home. Show email mismatch clearly. Use Better Auth sign-in via `/api/auth/*`. `inspect` and `accept` allow 10 calls per minute per IP; show the `TOO_MANY_REQUESTS` message as a wait-and-retry notice. If an account already uses the invited email, the error tells the person to sign in or use Forgot password first; link both.
- Add loading, empty, validation, error, and success states to both tables and all forms. Keep membership and invitation lists fresh after each mutation.
- Team requests: `members.list({ limit?, cursor?, status? })`, `members.update({ userId, role?, status? })`, `invitations.list({ limit?, cursor? })`, `invitations.create({ email, role })`, `invitations.revoke({ id })`, `invitations.resend({ id })`, `invitations.inspect({ token })`, and `invitations.accept({ token, name?, password? })`. Create/resend return `{ invitation, invitationUrl, emailSent }`.

## Phase 04: categories, attributes, tags

- Build `/categories` as a three-level-capable tree with create/edit form (name, slug, description, parent, order), reparent, sibling reorder, archive confirmation, product counts, and archived state. Consume `catalog.categories.*`; disable self/descendant parent choices and show server cycle errors.
- Build `/attributes` with attribute form (name, slug, display type select/swatch, order) and nested option editor (name, slug, swatch colour, order). Show usage counts, active/archived state, and archive confirmation. Consume `catalog.attributes.*`; exclude archived attributes/options from new product pickers while showing them on existing products.
- Build `/tags` with search, cursor pagination, create/edit form (name, slug, description), usage counts, and delete confirmation. Consume `catalog.tags.*`; show the in-use conflict message and link to affected products if available.
- Add URL-backed search/filter/cursor state and loading, empty, validation, error, and success states. Refresh product form option queries after taxonomy changes.
- Category requests: `catalog.categories.list({ limit?, cursor?, search?, parentId?, status? })`, `.create({ parentId?, name, slug, description? })`, `.update({ id, expectedUpdatedAt, name?, slug?, description? })`, `.reparent({ id, parentId, expectedUpdatedAt })`, `.reorder({ id, sortOrder, expectedUpdatedAt })`, and `.archive({ id, expectedUpdatedAt })`.
- Attribute requests: `catalog.attributes.list({ limit?, cursor?, search?, status? })`, `.create({ name, slug, displayType })`, `.update({ id, expectedUpdatedAt, name?, slug?, displayType? })`, `.reorder({ id, sortOrder, expectedUpdatedAt })`, `.archive({ id, expectedUpdatedAt })`. Options use `catalog.attributes.options.list({ attributeId, limit?, cursor?, search?, status? })`, `.create({ attributeId, name, slug, swatchValue? })`, `.update({ id, expectedUpdatedAt, name?, slug?, swatchValue? })`, `.reorder({ id, sortOrder, expectedUpdatedAt })`, and `.archive({ id, expectedUpdatedAt })`.
- Tag requests: `catalog.tags.list({ limit?, cursor?, search? })`, `.create({ name, slug, description? })`, `.update({ id, expectedUpdatedAt, name?, slug?, description? })`, and `.delete({ id, expectedUpdatedAt })`. Nullable descriptions and swatch values use `null` to clear them. Each list returns `{ items, nextCursor }`.

## Phase 05: products, variants, pricing

- Build `/products` with search, status/category/tag filters, sort, cursor pagination, row selection, and bulk publish/archive confirmation. Consume `catalog.products.list({ limit, cursor, search, status, categoryId, tagId, sortBy, sortDirection })` and `catalog.products.bulkStatus({ ids, action })`. Reflect status and conflict responses without optimistic status changes.
- Build `/products/new` and `/products/[id]` with name, slug, description, short description, categories, tags, product type, tax status, and tax class. Consume `catalog.products.create`, `.get`, and `.update` plus taxonomy list procedures. Send `expectedUpdatedAt` on every update and `catalog.products.setStatus` call; offer Reload on `CONFLICT`. Warn before leaving with unsaved changes.
- For a simple product, edit its one default variant inline. For a variable product, choose active attributes/options, mark each chosen attribute `useForVariants`, call `catalog.products.generateVariantCombinations({ attributes })`, and edit each returned combination. The `create`/`update` payload holds `attributes: [{ attributeId, useForVariants, optionIds }]` and `variants: [{ id?, name, sku, regularPrice, salePrice, saleStartsAt, saleEndsAt, stockStatus, manageStock, backorderPolicy, weight, length, width, height, isDefault, attributeOptions }]`. Remove a variant from the submitted array to archive it on save. Send money and dimensions as decimal strings. Product status changes use `catalog.products.setStatus({ id, status, expectedUpdatedAt })`. Never calculate final price on the client.
- Show publish prerequisites: at least one active priced variant, exactly one default variant, valid sale pricing/dates, and alt text on the primary image. Keep the media picker in the product editor (Phase 06). Confirm archive and bulk actions. Use server validation messages for duplicate SKU and stale revision.

## Phase 06: media

- Build `/media` as a responsive image grid with filename search, cursor pagination, alt text edit, archive confirmation, and “used by” product links. Consume `catalog.media.list`, `.get`, `.updateAlt`, and `.archive`. Show the active-product-use conflict.
- Add a product editor media picker: direct upload dropzone, library selection, drag reorder, one primary image, remove image, and alt text editing. Load current images and their order with `catalog.media.getProductMedia({ productId })`. Use `@better-upload/client` route `images` at `POST /api/upload`, then call `catalog.media.create` with the returned server-generated storage key and original filename. The server reads dimensions from the uploaded image. Call `catalog.media.setProductMedia` with ordered IDs, primary ID, and the product `updatedAt` revision. Refresh product detail after save.
- Accept only JPEG, PNG, WebP, and AVIF up to 10 MB in the picker. Show server errors for bad type, oversize file, invalid image content, missing upload, and stale product revision. Configure the IDrive e2 bucket CORS to allow the admin origin's direct PUT uploads and GET image display. Render `readUrl` returned by media procedures; it expires after 15 minutes, so refetch the query for a long-open screen. Never expose storage credentials.
- Media requests: `catalog.media.list({ search?, cursor?, limit? })`, `.get({ id })`, `.getProductMedia({ productId })`, `.create({ storageKey, originalFileName })`, `.updateAlt({ id, altText, updatedAt })`, `.archive({ id, updatedAt })`, and `.setProductMedia({ productId, updatedAt, mediaIds, primaryId })`. `mediaIds` is the ordered image list and `primaryId` is one of those IDs or `null` when the list is empty.
