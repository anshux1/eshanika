# Frontend work for Phases 07 to 10

These backend procedures are available under the admin app's `/rpc` route through `apps/admin/src/orpc/query.ts`. Build the pages with the existing page patterns, TanStack Query for server data, React Hook Form and the matching Zod schemas for forms. Server pages call `requireAdmin()` with the permission named below. Keep filters and cursors in the URL, invalidate affected list/detail queries after mutations, and show loading, empty, error, success, and permission states. All times arrive in UTC and should display in Asia/Kolkata. Money arrives as decimal strings and should be formatted, never recalculated in the browser.

## Phase 07: inventory

- Build `/inventory` with a responsive table of managed-stock variants: product, variant, SKU, on hand, reserved, available, reorder point, and stock status. URL filter `stock=all|low|out`; cursor pagination from `inventory.list({ stock?, cursor?, limit? })`. Require `inventory.write` on the page.
- Add an Adjust dialog launched from a row. Inputs: signed integer `quantityDelta` (nonzero), `reason` (`restock`, `adjustment`, `damage`, `initial_stock`), optional note (max 1000), and a UUID `idempotencyKey` generated once when the dialog opens. Show current and projected on-hand/available balances before submit. Call `inventory.adjust({ variantId, quantityDelta, reason, note?, idempotencyKey })`. Preserve the key when retrying the same submit; generate a new one for a new adjustment. Disable submit while pending and show the below-reserved conflict clearly. Refresh inventory and ledger queries after success.
- Build `/inventory/movements` with URL filters for `variantId`, `reason`, `from`, `to` (ISO timestamps), cursor pagination, quantity delta, balance after, actor, and reference. Consume `inventory.movements({ variantId?, reason?, from?, to?, cursor?, limit? })`. Add CSV download using `inventory.exportMovements({ variantId?, reason?, from?, to? })`, which returns `{ fileName, content }`; create a browser Blob and download it. Display validation for reversed date ranges.

## Phase 08: customers

- Build `/customers` with search by partial name, email, or phone and URL-backed cursor pagination. Show name, email, phone, order count, total spent, and last order date. Consume `customers.list({ search?, cursor?, limit? })`. Require `orders.read`.
- Build `/customers/[id]` with profile, saved addresses, the active cart with product/variant quantities, and a cursor-paginated order history. Consume `customers.get({ id })` and `customers.orders({ customerId: id, cursor?, limit? })`; each order links to `/orders/[id]`. Keep this screen read only. Show a customer-not-found state for `NOT_FOUND`.

## Phase 09: orders

- Build `/orders` with search by order number or billing email; status, payment status, fulfilment status, and date filters; URL-backed cursor pagination. Consume `orders.list({ search?, status?, paymentStatus?, fulfillmentStatus?, from?, to?, cursor?, limit? })`. Require `orders.read`.
- Build `/orders/[id]` with an overview and tabs/sections for item snapshots, billing/shipping address snapshots, subtotal/discount/tax/shipping/fees/total, coupon, payment summary, timeline, internal notes, and shipments. Consume `orders.get({ id })`. Print a packing slip from the same order snapshot using a print stylesheet or print route; include order number, shipping address, item names/SKUs/quantities, and no internal notes.
- Add Confirm/Process status actions for users with `orders.write`, based on the server transition table. Call `orders.transition({ id, to, note? })`; shipment-driven statuses come from Phase 10. Add internal note form `orders.addNote({ id, note })`. Add cancel confirmation with required reason and one UUID idempotency key per attempt: `orders.cancel({ id, reason, idempotencyKey })`. Refresh detail, list, inventory, and ledger after cancellation. If the result has `refundNeeded: true`, show a clear refund-needed message and link to the Phase 12 payment/refund section; cancellation never triggers a refund.

## Phase 10: fulfilment and tracking

- Put shipment creation and shipment timelines in the Fulfilment section of `/orders/[id]`. Require `orders.write` for actions, `orders.read` for viewing. Show each order line's ordered quantity and already assigned shipment quantity. The create form lets staff select one or more items and positive quantities, carrier, optional tracking number, optional tracking URL, and optional estimated delivery timestamp. Generate one UUID `idempotencyKey` per form attempt and call `fulfilments.create({ orderId, idempotencyKey, items: [{ orderItemId, quantity }], carrier, trackingNumber?, trackingUrl?, estimatedDeliveryAt? })`. The server rejects quantities above the unassigned amount; display that conflict and reload the order.
- For each shipment, show status, carrier/tracking link, item quantities, estimated delivery, shipping/delivery dates, and event timeline from `orders.get`. Add allowed status actions: pending → packed → shipped → out_for_delivery/delivered/failed/returned, including failed recovery. Call `fulfilments.transition({ id, to, description?, location?, failureReason? })`; require a failure reason when marking failed. Confirm the shipped action because it consumes reservations and writes sale movements. Refresh order and inventory queries after status changes.
- Add an event form for descriptive tracking updates without changing status: `fulfilments.addEvent({ id, description, location?, occurredAt? })`. The returned event appears in the shipment timeline after invalidating `orders.get`. Use the order's `fulfillmentStatus` and `status` from the server; do not derive them in the browser.
